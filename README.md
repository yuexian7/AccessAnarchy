# Access Anarchy（出入口无碰撞）

> 游戏内模组名会按语言显示本地化版本（中文＝出入口无碰撞，12 语对照见 `归档-版本史.md` §⑥）；Paradox Mods 上的显示名始终是 `Access Anarchy`——发布接口只有一个 `displayName`，无法按语言切换。

**都市：天际线 II (Cities: Skylines II) 代码模组 · 适配游戏版本 1.6.2f1 · 零 Harmony 补丁**

让车辆在通过停车场、仓库、商场等建筑物的出入口时不再因行人减速停车，直接穿过行人；行人的行走行为、车辆之间的避让完全不受影响。

## 它解决什么问题

原版游戏中，建筑出入口（停车场匝道、商场/仓库的连接道、停车楼坡道）是车辆与行人冲突的高发点：只要有行人横穿，车辆就会排队等待甚至堵死整个出入口。本模组按照 Anarchy 系列模组的设计哲学（"优先 ECS 数据编辑而非 Harmony 补丁"），通过编辑共享 ECS 数据实现该行为。

## 工作原理（一句话版）

游戏里车辆避让行人的唯一动态机制，是车辆读取自己车道的 `LaneOverlap`（车道重叠关系）缓冲，看到重叠的行人道上有行人登记就刹车。本模组用一个 ECS 系统**持续删除"出入口车道 ↔ 行人道"的重叠条目**——车辆看不到行人道，自然不再减速。行人自己根本不读这份数据，所以行人行为不变；车辆之间的重叠条目原样保留，所以车-车避让不变。

没有 Harmony 补丁、没有系统替换、没有改动任何游戏方法。

## 设置

模组选项页（主菜单或游戏内 → 选项 → 模组 → Access Anarchy）：

| 选项 | 默认 | 说明 |
|---|---|---|
| 车辆穿过行人 | 开 | 总开关。关闭后会触发一次车道重叠关系重建，完全恢复原版行为（关闭瞬间会短促卡顿，属正常）。v0.8.10 起恢复改为三档阶梯：先用最省的办法，不够再加重；并且会在后台继续重试，**恢复失败也不需要退出重进存档**（除非日志明确要求）。v0.8.11 起"有没有恢复"的判据多加了一把尺子（和关闭那一刻对比），中途大修大建之后不会再误报"没恢复" |
| 取消避让范围 | 仅出入口区域 | `仅出入口区域` 或 `全部道路（全局）`。仅出入口区域＝建筑出入口、车库坡道、停车场与建筑内部道路这一整片；全局模式会禁用全市所有车让人行为，含人行横道（有信号灯的路口仍会因红灯停车，那是原版信号灯逻辑，不是让行人）。**「全局」的字面含义：凡是会为行人减速的车道都覆盖——汽车、货车、自行车道、电车轨道、火车轨道都一样**（电车/列车是 v0.8.10 补上的，原版里它们本来也会在道口为行人减速）。其余几种"开了模组仍然停车"的原因见下面的《为什么有些路口/出入口开了模组仍然会停车》 |

「自定义标记」板块（**v0.8.3 只是占位，三条全部标灰不可点，功能在 v0.9.0 实现**）：计划提供「建筑和设施」「人行横道」「路口」三项，开启后点击对应对象即可把它设为无碰撞模式，且不受总开关与「取消避让范围」的限制。

范围就这两个开关，v0.8.2 及以前的「出入口区域选择」三条勾选项已合并进「取消避让范围 · 仅出入口区域」：停车场、建筑与外部道路的车辆出入口、建筑内部道路现在同开同关。三轮实机证明这三类在数据上分不开（停车场大门与商店大门是同一种 `ConnectionLane`），而"紧邻出入口"这条兜底天生跨类，留着只会让玩家看到互相覆盖。

v0.8.5 起「仅出入口区域」的覆盖面补上了一类漏判：仓库、商超那种**货运/装卸口**连道（原版只给它 `Inside|AllowCargo`，不带 `Road|Track|Parking`），此前只有全局模式覆盖得到，两种模式对"哪些是车行道"给出相反答案，表现就是"部分建筑生效、部分不生效"。v0.8.6 把这条判据补全到**两种模式都认**货台那一类（并且仍然严格排除带 `Pedestrian` 位的室外行人连道，那是人行道不是车行道）。

人行横道在 v0.8.6 起按**车道归属**区分，不再是"出入口模式一条都不删"的一刀切：

- 挂在**出入口/建筑内部道路**上的横道条目（停车楼坡道口、场区道路、仓库装卸区那种资产门口的横道）→ 一起删，车辆直接穿过；
- 挂在**市政道路与路口**上的横道条目 → 一条不动，马路上的斑马线照常礼让行人。

也就是说"不影响道路上的横道"这条底线没有变，变的是资产自己地界内那条横道不再卡住车辆。全局模式下仍然是所有车让人行为一律关闭。

切换范围后范围变窄的那部分不会自己回来，模组会请游戏重建一次车道重叠关系再按新范围重删，所以会有一次短暂卡顿，属正常。**请勿在游戏中短时间内频繁修改设置**，连续切换容易让某一轮重建没落地就看到混乱结果。

快捷键（在选项页「快捷键设置」板块里，位于「自定义标记」下面；可改键、可清空，改键会持久化）：

|---|---|
| 开启/关闭本模组 | 总开关的快捷键 |
| 切换取消避让范围 | 在「仅出入口区域」与「全部道路（全局）」之间切换 |

首次订阅时这两行都是空的，需要玩家自己按一个键；设过之后重启游戏会照玩家存的走，不用
再管。给玩家推荐几个原版没占的裸键：h / j / k / n、F6、F7、F8、F10-F12、数字 4-0。

⚠ 别把这两个键设成原版已占用的裸键（R/T 是相机缩放与旋转、F/G/Q/E、X/Z/B/M/L、空格、PageUp/PageDown 等都在原版表里）：游戏会弹「快捷键重复」提示，并且**在冲突期间直接把模组的热键动作禁用掉**，局内按了没反应。判据与完整按键表见 `归档-版本史.md` §⑤。

**模组快捷键优先**：本模组的快捷键优先响应，建议不要与其它模组使用同一组键，否则对侧模组可能收不到那次按键。

设置自动保存，改动即时生效，无需重启游戏。

## 为什么有些路口/出入口开了模组仍然会停车

有玩家反馈"看起来一模一样的交叉口，有的生效有的不生效"。排查结论：**本模组只删一种数据（车辆车道上指向行人道的重叠条目），原版让车辆减速停车的通道不止这一种**。下面这几类都与行人避让无关，本模组刻意不去改它们（改了就不再是"出入口无碰撞"，而是重写驾驶行为了）：

| 现象 | 机制（反编译位置） | 怎么分辨 |
|---|---|---|
| 有信号灯的路口照样停 | 车道自己的 `LaneSignal` 为 Stop 时直接压制通行（`CarLaneSpeedIterator.cs:138-149`），跟有没有行人在过街无关 | 把路口的灯拆掉/换成环形交叉口，若立刻变流畅就是这个 |
| STOP / YIELD 标志路口 | 原版写在 `CarLaneFlags.Stop`/`Yield` 上，是**车道属性**不是重叠条目（同文件 :438-443） | 看路口有没有那个牌子 |
| 路口被前车占满、排长队 | 车辆要"路口净空"才敢进（同车道的重叠对象、车道预约 `LaneReservation`、`CheckOverlapSpace`，同文件 :1283-1318） | 车是**停在车队尾巴**而不是停在行人面前；行人早走完了它还是不动 |
| 行人正站在你要走的那条车道上 | 这已经不是"避让"而是"前面有物体挡路"：读本车道自己的 `LaneObject` 登记（同文件 :1105-1125） | 车辆会绕过行人而不是原地等；把乱穿马路的人流分开即可 |
| 车压在人行道/广场地面上时龟速 | 车辆所在车道带 `PedestrianLane` 时被限速到 20 km/h（同文件 :194-196），与本模组的删除动作无关 | 只在"车开上了人行道"的那段路上出现 |
| 出入口旁边那条市政道路上仍然让行人 | 出入口模式下挂在市政车道上的行人/横道条目按设计保留 | 想要全部关掉，把「取消避让范围」切到「全部道路（全局）」 |
| **暂停一会儿再继续，之前不停车的地方又开始让行人了** | 游戏的道路重叠重建挂在**渲染帧**上（`ModificationSystem` → `Modification4B`），暂停时照样每帧跑；而本模组挂在**模拟步**上，暂停（速度 0）时一步都不跑，所以这段时间里游戏写回来的条目没人重删。v0.8.7 之前全局模式尤其明显：全局只有一次全城剥离，漏了就永久漏 | v0.8.7 已修：模组会用"渲染帧数比模拟步数多出一截"量出这种暂停窗口，并在恢复运行后的几秒内补剥（出入口模式起一轮重建，全局模式做一次全城重剥）；v0.8.11 起出入口模式若在自检里读到残留还会**当场**补剥一次，见下面 `Access set audit` 的自愈行。若还在复现，看日志 `Global sweep driver: … N blind window(s) …` |

判断"到底是不是漏删"的唯一硬证据是日志（不要靠肉眼猜）：`Access set audit: …`、`Global sweep driver: …`，与全局模式下的 `Overlap coverage (global): … street & intersection lanes X of Y hold Z …`。**Z=0 就说明路口车道的行人条目确实一条都不剩**，车还停就是上表那几类原因；Z 连续两次心跳都非零，才轮到把它当本模组的缺陷来查（把日志发来，v0.8.7 起这条读数后面还会跟最多 3 行 `Overlap leak sample:`，直接给出漏的是哪条车道、在地图哪个坐标、指向哪种对端车道）。

v0.8.11 起出入口模式的 `Access set audit` 换成**与剥离动作同一把尺子**数（市政道路上按设计保留的人行横道条目不再算进"残留"），两个数 X/Y 现在**都是**这把尺子读出来的，所以干净稳态就应该是 `0 of 3227 vehicle lanes still hold 0 pedestrian overlap entries`——X 或 Y 任一非零才是真漏口（v0.8.11 第一版只换了 Y 那一格，X 仍会把"挂着设计保留横道条目"的车道数算进来，读成"787 条车道仍然挂着 0 条条目"这种自相矛盾的行，收尾补丁已把两格对齐）。万一真的读到残留，**连续两次读数非零**（不要求两次数值相同）就会触发一次当场补剥（日志跟一行 `Access set audit: the leak survived 2 consecutive readings - re-stripped the whole vehicle set now (self-heal…)`），不用等整轮重建兜底。频率上限由审计自己的降频夹着（审计点最密 = 每个心跳，一个心跳 1800 模拟步，实测 ≈4~8 秒）：静置图约 32~64 秒一次，施工期最快约 8~16 秒一次——不会变成每帧动作。

v0.8.10 起这两类读数由**同一遍**扫描算出（此前出入口模式与全局模式各扫一遍，同一次心跳付两笔全量扫描），所以每次读数少一半卡顿；两个数字现在也同源，不会互相矛盾。

## 兼容性

- **零 Harmony 补丁**——不存在补丁被其他模组 `UnpatchAll` 拆掉的问题，也不与任何基于 Harmony 的模组（Traffic、Skyve 等）产生补丁冲突。Skyve / 模组管理器本身只是管理器，不是交通模组。
- 与修改交通行为的模组理论上可共存：本模组不持有任何游戏侧缓存，删除会在游戏重建重叠关系之后重新应用——事件驱动（跟随重建闸门）之外，v0.8.7 起还有两道兜底：出入口模式的整轮重建、全局模式的条件式全城重剥（暂停窗口、车道数变化、或最长兜底周期触发）。别的模组怎么改车道数据都不会导致永久性不一致；关闭或缩小避让范围时会请游戏重建全市重叠关系，不会留下残留状态。
- Realistic Path Finding 等改行人寻路的模组不受影响：行人寻路不读取本模组删除的 `LaneOverlap` 数据。
- v0.8.4 起本模组**不再改动行人车道自己**的重叠数据（人行道、人行横道、建筑的人行大门道）。以前的判定把行人设施误认成"车辆出入口"，可能连带影响红绿灯划分行人相位（`TrafficLightInitializationSystem.cs:515-530` 读的是行人侧缓冲）；现在这类实体一律出局。

**被我们改过的那份数据还有别的读者**——这是"没报错但可能有效果差别"的真正来源，逐条按 1.6.2f1 反编译核对过：

| 读者 | 它用这份数据做什么 | 删掉行人条目后会怎样 |
|---|---|---|
| `CarLaneSpeedIterator.CheckOverlappingLanes` | 车辆让行行人（本模组的目标） | 目标效果 |
| `SecondaryLaneSystem.cs:1486-1512` | 给人行道/自行车道在交叉处算"切断区间"（分安全/不安全过街） | 我们只碰车辆车道，带 `CarLane` 的**自行车道**在全局模式下也在范围内，交叉口的切断区间可能随之变化。影响面很小，v0.5 起一直如此，未收到反馈 |
| `TrainLaneSpeedIterator.cs:466-468`、`:512` | **电车/火车**在道口同样为行人减速（与汽车同一条 `LaneOverlap → LaneObject → Creature` 通道；`Game.Prefabs.TrackLane.GetArchetypeComponents` 也确实贡献 `LaneOverlap` 缓冲） | 全局模式下轨道车道一并纳入（v0.8.10），道口的有轨电车/列车不再为行人减速——这是「全局」模式的应有之义。出入口模式不含轨道，列车其余行为不变 |
| `VehicleUtils.cs:1491-1536`、`ParkedVehiclesSystem.cs:158-215`、`FixParkingLocationSystem.cs:576` | 判断车位能不能用（把与它重叠的车道当"车道口"绕开），这里**不按行人/车辆过滤** | 停车场内的车位可能接受原版会拒绝的位置（车辆更愿意往里停）。方向上是"少绕行人"，与模组意图一致 |
| `TrafficLightInitializationSystem.cs:515-530` | 信号灯划分行人相位 | 读的是行人侧缓冲，v0.8.4 起我们完全不碰 |
| `NavigationDebugSystem.cs:730` | 调试可视化 | 只影响调试显示 |

据此，**理论上可能相互影响的模组类型**（都不报错，只是行为叠加）：

1. 自己重写"车辆是否让行行人"的模组（改 `CarLaneSpeedIterator`、或给车辆加"避让行人/避让非机动车"逻辑的 AI 模组）：它们看不到我们删掉的条目，于是那部分功能在出入口区域（全局模式下是全部道路）会**失效**——表现是"装了本模组后另一个模组的让行行为没了"。
2. 自己写 `LaneOverlap` 的模组（自定义路口/斑马线编辑器、"取消人行横道"一类）：同一份数据两边都会改，谁在同一模拟步里最后写谁生效。本模组跟原版重建闸门同步重删，通常是我们赢，但双方会互相拉扯，**不建议同装**。
3. 用自定义资产改变车道类型的模组：判"这条连道是不是车走的"读的是原版那组 `ConnectionLane` 标志位（`Road|Track|Parking|AllowCargo`）。若某个自定义资产把行人专用连道标成车行位，它会被识别成出入口；反之，标了非标准位（例如只给 `Outside`）的车辆连道会被识别成"不是出入口"，表现就是那处不生效。
4. 修改车辆碰撞/推挤逻辑的模组（取消碰撞、车辆互穿一类）：与本模组改的是不同数据（本模组不碰 `CarLaneFlags.PushBlockers` 与物理碰撞），可叠加，但两者同时开时"车不让人 + 车不让人 + 行人本体在车道上也不减速"会叠加成完全无碰撞，事故/穿模观感会更强。
5. 大幅提高道路限速的模组：车辆 AI 本身会失真甚至卡死——这是原版运动学模型的上限（每条模拟步的位移长度就是车速、过路口时原版还主动把加减速上限抬到 1000 km/h，机制见 `归档-版本史.md` §⑰），与本模组改的数据无关。

判断"是不是本模组导致的"，用日志而不是猜：`Rebuild gate:`、`Anchor grid:`、`Access set audit:`、`Overlap coverage (global):`、`Global sweep driver:` 五行能说明模组到底改了多少数据、有没有跟丢。关掉功能后"车辆没恢复让行"另看两行：`Restore baseline:`（关闭那一刻实测还剩多少条目，是恢复判据的第二把尺子）与 `Restore check #N …`（末尾会写明成立的是哪条腿：`enough via baseline80(...)` 或 `disable-delta(+N/M)`）；`Stripped-lane ledger:` 则说明定向恢复要标多少条车道。

## 卸载安全（长期约束，每个新功能都要过这条）

取消订阅、直接删掉模组文件夹、或在模组管理器里关闭本模组之后，下次进入游戏**不需要**本模组在场也不会出问题：出入口避让自动恢复原版，日志里也不会出现与本模组有关的报错。这不是"理论上安全"，而是三条机制共同保证的：

1. **不往存档里写任何模组自有数据**。本模组没有声明任何组件类型，对世界数据的改动只有两类：改车辆车道 `LaneOverlap` 缓冲里的条目（且只改游戏已有该缓冲的实体，从不新增缓冲），以及临时给实体加原版自己的 `Updated` 脏标记。后者由原版 `CleanUpSystem` 在每帧 Cleanup 阶段移除，与模组是否存在无关。
2. **游戏每次进入地图都会全量重建重叠关系**。原版 `LaneOverlapSystem.OnGameLoaded` 把 `m_Loaded` 置位（`Net/LaneOverlapSystem.cs:1899-1902`），下一次 `OnUpdate` 即改用"全部 owner / 全部车道"查询并把 `m_UpdateAll` 打开（`:1917-1919`、`:1954`），逐条车道 `bufferData.Clear()` 后重算（`:1077`）。这条路径在**每次进图**时都会走（不只是读档），所以模组不在场时，被删掉的行人条目必然由游戏自己补回来。
3. **模组消失后没有任何东西需要被解析**。不打 Harmony 补丁；不注册游戏会按名字/类型回查的持久对象；热键走 `ModSetting` 自己的输入映射，不会进游戏的键位设置文件；设置与键位只存在模组自己的 `AccessAnarchy.coc` 里，而游戏读的是硬编码列表、不扫描该目录——模组没了，这个文件就只是被忽略。

配套的四处防御：v0.8.5 起 `OnDispose` 里注销选项页那一句包在 try/catch 里（它抛出会让 `Setting.Instance` 清不掉、并在 Player.log 留下一条属于本模组的卸载错误），键位诊断在 `InputManager.instance` 已为 null 的关机序列里直接跳过；**v0.8.10 起卸载时还会把 12 个本地化翻译源还给游戏**（`LocalizationManager.AddSource` 是往列表里追加、`RemoveSource` 没人调，官方模板也一样——不还就会在"关掉再打开"一次之后永久多挂一份旧翻译）。

### 关闭之后怎么恢复原版（v0.8.10 起三档阶梯）

关闭开关或把范围调窄时，模组不会自动"撤销"，而是请游戏自己把车道重叠关系重建回来。三档由轻到重，**每一档都由日志里的审计读数判定是否生效，而不是假设它生效**：

| 档次 | 做法 | 代价 | 什么时候用 |
|---|---|---|---|
| 1 | 反射让游戏走一次全量重建（与读档同一条路径） | 最省，但依赖游戏的一个内部字段名 | 默认；游戏更新后如果这条路失灵，日志会写 `Reflection restore path is not consumed by the game`，并自动改用下一档 |
| 2 | 只给"模组真正改写过的那几百条车道"的归属对象打脏标记 | 与改动量成正比，同样不依赖任何内部字段名 | 第 2 轮检查不达标时，以及后台重试 |
| 3 | 全城全部车道打脏标记（= 一次世界加载同量级的重建） | 最重，**只跑一次** | 第 3 轮仍不达标时的最后一搏 |

五轮检查都失败也不会就此放弃：模组会在后台每 ~24 秒重试一次（最多 5 次，每次都用最省的两档，并立刻扫一遍判定），所以**绝大多数情况下不需要退出重进存档**。只有日志打出 `Background restore gave up after 5 retries` 时才需要重进地图。

配套的两处防御（v0.8.5）：`OnDispose` 里注销选项页那一句现在包在 try/catch 里（它抛出会让 `Setting.Instance` 清不掉、并在 Player.log 留下一条属于本模组的卸载错误）；键位诊断在 `InputManager.instance` 已为 null 的关机序列里直接跳过。

## 性能

本模组是纯 ECS 数据编辑，不hook任何方法调用，稳态开销来自下面五件事：

1. **出入口区域的重建**。模组要把"车辆出入口 + 其附近路段"的车道挑出来，删除它们指向行人道的重叠条目。v0.8.4 起这件事**只在有变化时发生**：车道数量变了（施工/建拆）、或原版自己重算过某批车道的重叠关系；v0.8.5 起"原版重算过"是**即时**起轮信号（上一轮跑完后至少隔 256 模拟步再起，按作者实机测得的 ≈225 步/秒约 1.1 秒），不再等下一个 512 步检查点。一张图放着不动时，只有每 8192 步一次的长兜底，v0.8.9 起这条兜底**另外**要求墙钟满 30 秒（"8192 步"在墙上的长度会随模拟速度档变，同一个存档实测 ≈225 步/秒 ⇒ ≈36 秒）。以前是每 2048 步无条件全量重建一遍，大城市里那基本是白烧一条 worker 线程——玩家反馈的"帧数正常但模拟变慢"就是它。v0.8.9 又把"变化"这两条判据收紧了一次：**候选车道数**要变够量（64 条或 1%）才算数，**锚点数**要同一个新数值连续两个检查点都看到才算数（这类计数会被停车场/临时车道来回加减，作者实机那局的"车辆集合条数"就是 3596 → 3593 → 3587 → 3592，旧写法每个 512 步检查点都能凑出一轮整城重建；去重只多等一个检查点 ≈2.3 秒）；新建停车场/建筑仍然当检查点被接住，因为它同时会打开原版重建闸门，那条路径没动。
2. **锚点范围**。"仅出入口区域"除了出入口车道本身，还包括紧邻出入口的路段（32 米）。v0.8.4 起锚点只从**车行车道**采集；此前人行道、人行横道、建筑的人行大门道也被当成出入口，在一位作者的实测存档里让锚点来源从 4.8 千条虚增到 11.1 万条，覆盖车道从停车场周围扩到全城 51% 的车道，扫描量随之放大一个量级。v0.8.10 起轨道车道（电车/火车）也不再参与出入口模式的锚点距离测试——它不进范围，没必要白算。
3. **每帧的跟随检查**。原版在修路建拆时会重算重叠关系，模组要跟上去重删。这一步按原版同一个闸门取实体，正常游玩时匹配到的数量与原版自己做这件事相同，不会额外放大。⚠ 但这个闸门只在模拟推进时看得到：游戏的重建挂在**渲染帧**上，暂停时照样跑，而本模组挂在**模拟步**上，暂停期间一步都不跑（v0.8.7 的根因，见第 5 条）。
4. **空转的固定税（v0.8.5）**。原来每个模拟步都要向游戏申请一次命令缓冲、排一个查询必然为空的跟随 job、再把自己登记成 barrier 的生产者。单次只有几微秒，但乘上每渲染帧的 1–8 个模拟步就是长期白付；现在这一步开头先判"到底有没有活"，没活直接返回，什么都不申请。
5. **全局模式的全城重剥（v0.8.7）**。"全部道路（全局）"以前只在进图/切模式时做一次全城剥离，之后完全依赖第 3 条那个闸门——于是任何一次闸门没跟上的重建（暂停期间发生的那些）都会永久留在原版状态，这就是"开了全局反而不如仅出入口生效"。现在全局模式与出入口模式共用同一套调度：探测到暂停窗口、或车道数变了、或到最长兜底周期时，做一次全城重剥，并且两次之间至少隔 256 模拟步。这张扫描是**只读**的：没有行人条目的车道在计数为 0 时直接返回，不申请任何命令缓冲写入，所以稳态那张没动过的图上是"扫一次、什么都不写"。⚠ v0.8.9 修掉了**两个**自己造成的形状。一是判据原本是"与上一次重剥时记的实体数不同就再来一次"，而**正在经营的城**里带重叠关系的车道数会被车位/临时车道来回加减（实机 6745 ↔ 6739），±几条也算"变了"。二是**最长兜底只用步数量计量**：作者 2026-10-07 两局日志里全城重剥的间隔分别是 8~19 秒与 ≈36 秒，我先把这个频次归给了第一条，是后一局把它否证的——那局 `overlap entities 6751 -> 6751`（Δ 全程 0）、34 个检查点全部 skipped，两次 sweep 之间正好 8192 步 ≈ 36 秒 ⇒ 起 sweep 的是兜底，而"8192 步"在墙上的长度随模拟速度档变，步率高时就被同比压缩。两处分别修：变化门槛（全局 256 条或 2%，出入口 64 条或 1%）并把基线改成每个检查点前移；兜底改成"8192 步**且**满 30 秒"，日志行也跟着写成 `fallback every 8192 steps or 30s, whichever is later`，免得下次又靠猜。出入口那一侧同步处理，但用的是另一种形状：**候选数**变够量才算（64 条或 1%），**锚点数**不加数值门槛、只要求"同一个新数值连续两个检查点都看到"（一个小停车场的锚点增量和噪声同量级，用阈值会把它一起挡掉，所以让它靠"持续"而不是"够大"过关）。另外，本周期原版重建闸门已经开过（我们跟着它当帧重删过）时，检查点不再另外起一次全城重剥——那批活儿已经干过了，重复扫全城正是 v0.8.4 压下去的那笔开销（这条从 v0.8.7 起就写在注释里，代码到 v0.8.9 才真的做到）。

如果你在启用模组后仍感到明显掉帧或模拟变慢，请带 `...\Cities Skylines II\Logs\AccessAnarchy.AccessAnarchyMod.log` 里这几行来反馈：`Access Anarchy v… loading`、`Anchor grid: … vehicle source lane(s) -> …`、`Access-zone rebuild driver: … round(s) started, … check(s) skipped`、`Global sweep driver: … sweep(s) run … blind window(s) …`、`Access set audit: …`、`Overlap coverage (global): …`。它们能直接说明模组在做多少工作，而不需要靠猜。

v0.8.6 新增的 `Overlap coverage` 是**跟着事件走的诊断**：在"首次全量或全城重剥刚跑完"、"这一周期里原版真的重算过重叠关系"、"这一周期重剥又叫走过条目"三种时刻才扫全城，稳态一次都不扫——不会变成每条模拟步的固定税。v0.8.7 起它后面可能跟最多 3 行 `Overlap leak sample:`（只有真数到"该剥没剥干净"的车辆车道才会写），给出那条车道的类型位、地图坐标与对端车道的 flags。⚠ v0.8.9 把这两行诊断自己的税降下来：后两种触发时刻在施工期几乎每个心跳都成立，而扫描本身要"同步等在飞的 job + 全城遍历 + 主线程求和"（大城 10–30 ms），现在只有"刚做过首次全量/全城重剥"那一次是即时的（这条必须即时，它是"重剥到底有没有效"的证据），其余情况每 4 个心跳采一次。**v0.8.10 再降一半**：出入口模式的集合审计原来还单独扫一遍集合（实机 6.5 万条 ⇒ 主线程阻塞 15–40 ms），现在两个口径由同一遍扫描算出，一次心跳只付一次阻塞。

v0.8.7 新增的 `Global sweep driver` 同时是性能与正确性的读数：`sweep(s) run` 是全局模式做过几次全城重剥（v0.8.9 后的封顶就是那条兜底——"8192 步且满 30 秒"，作者实机读数 ≈36 秒一次；只有暂停窗口/真正的施工才会加密度），`blind window(s)` 是模组探测到"游戏在跑而我们在暂停"的窗口次数，`re-stripped … entries` 才是这次重剥真正又叫走了多少条——**长期为 0 说明全局模式没有漏口，长期非 0 说明漏口确实存在且已被这条兜底补上**。v0.8.9 起这行还带 `overlap entities X -> Y, gate 256 / 2%` 和 `N check(s) skipped`：Δ 不过门槛就不该有新的 sweep，若门槛挡不住（Δ 一直很大）就说明那批车道真的在被持续改写。⚠ 反过来别把它读反：**Δ=0 而 sweep 仍在慢慢涨是正常的**（那是 8192 步兜底在跑，实机就是 `6751 -> 6751` 配 34 次 skipped 还在起 sweep），漏不漏只看 `re-stripped … entries` 连不连续非 0。

游戏**原生闪退**（不是报错、不是行为异常）时别猜：Windows 的 `%LOCALAPPDATA%\CrashDumps\Cities2.exe.<pid>.dmp` 里有完整转储，本仓库 `node tools/crash-triage.mjs "<dmp 路径>"` 直接给出异常码、被访问地址、故障指令所在的**完整模块路径 + 偏移**、崩溃线程栈上各模块的返回地址计数。`node tools/pe-func.mjs <RVA>` 再把原版 `lib_burst_generated.dll` 的偏移映射到函数区间。2026-10-07 两次"资产预览即崩"就是这样定性的（两次同一条指令、故障点就在原版 Burst 函数内，详见 `归档-版本史.md` §⑱）。

⚠ **判据要分崩溃类型，别只会看栈**：堆损坏 / 释放后使用这一类（症状是崩在 `UnityPlayer.dll` 的分配器或链表遍历里、故障地址像 `0x0`+小偏移或 `0xFFFFFFFF` 一类投毒值、托管栈常常整个为空），**肇事点与崩溃点天然分离**，"崩溃线程栈上没有本模组"**不能**用来免责——这条曾被用来免责并被明确推翻。这类崩溃只能靠"崩点是否紧贴我们的写窗口 + 有没有配对的内存序证据"来判断；反过来，崩溃点确实落在我们自己的指令/函数区间内（如 10-07 那两次），才是可以直接定性的。分不清类型时，结论就只能写"证据不足"。
